On 2026-11-05 two hidden displays (S2721DGF, AW3425DW) came back off-input after wake. The wake journal went to `needsAttention` ("display topology no longer matches this removal"). Clicking Restore appeared to do nothing, and the unified log had no `show ... refused=` entry, so the click probably never reached `AppModel.show`.

**Findings**

- Menu bar (`AppDelegate.addDisplayMenuSection`): a needs-recovery display with no runnable action is added as `disabledItem(tile.name)`, so clicking it does nothing. A blocked Show is also disabled, with the reason only in a tooltip. The separate "Review Display Recovery…" item opens only `handoffStatus.target`, not the display you clicked.
- Settings (`DisplaySettingsView.primaryAction`): the same state offers only "Check Again", which refreshes silently and gives no feedback when nothing changed.
- Labels differ: Settings says "Restore" for needs-recovery displays while the menu says "Show".

**Proposed direction**

- Menu: when a display needs recovery and Restore can run, show it enabled as "Restore NAME". Otherwise make the item enabled, have it open Settings on that display, and give it the subtitle "Needs recovery". Show "Review Display Recovery…" only when no display row covers the problem, matching the banner rule in `AppModel` (`displayRecoveryProblem` banner guard).
- Settings: Check Again should report a result when nothing changed. Any refused Restore should show its reason inline.

Read-only diagnosis only. Restore behavior and journal rules are unchanged.

## Acceptance criteria

- [ ] Menu bar: a needs-recovery display row is never a disabled no-op; it runs Restore when allowed, otherwise opens Settings on that display
- [ ] Settings: Check Again and refused Restore show a visible result or reason
- [ ] Focused app tests cover the menu item action for runnable and unrunnable needs-recovery tiles
